# 墨池改造守则（不劣化契约）

> 适用：M0→M3 收敛加固阶段（仓库独立与基线整顿 → 阅读模块收口 → 安全与 AI 成本加固 → 工程化部署与测试）。
> 目的：保证每一步改动都可验证、可回退、可追溯，**不会越改越烂**。
> 本阶段铁律：**不新增功能模块**，只做收敛、收口、加固。

---

## 1. 四条第一性原理（源自比对对象，每步改动前自查）

1. **闭环原理**（novel-plus / inkos）：功能"做了一半等于没做"。
   自查：这个改动是否让某条用户路径（后端端点 ↔ 前端入口 ↔ 数据库）从头走到尾？
   后端有的端点前端必须有消费；前端展示的入口后端必须有支撑。

2. **记忆与边界原理**（SillyTavern / WinkNovel）：AI 设定、角色、历史要可结构化持久化、可复用；
   输入输出必须有边界（上限 / 配额 / 防注入 / 成本可控）。改动涉及 AI 时必查这三样。

3. **内容可治理原理**（novel-plus / NodeBB）：用户内容可审核、可追溯、权限边界清晰。
   凡涉及他人可见内容的改动，必须确认越权/删除/可见性没有漏洞。

4. **精确到段落原理**（legado）：阅读相关的落点（书签/批注/好句/进度）必须精确、可恢复、口径正确。
   不许出现"索引恒为 0 / 计数口径错 / 点了不跳转"这类假功能。

每次改动用一个最小提问收尾：**"这一步让哪条链更闭环？"** 答不出就不算完成。

---

## 2. 单步操作规程（Step Loop，一步一做）

```
[Step N] 一句话目标 + 改动文件清单
  0. 基线：确认当前状态为"上一轮绿灯"（或记录了已知红点），先 git commit 干净基线
  1. 改动：最小 diff，只碰目标文件，禁止顺带改无关代码
  2. 自测：改动相关的单测 / 接口冒烟 / 前端 build
  3. 回归：pytest 全量 + npm run build + 关键路径手测清单（见 §4）
  4. 提交：git commit（语义化 + 引用变更登记条目号）
  5. 停靠：全绿才进下一步；出现我造成的回归 → 立即修复或回滚，禁止带病前进
```

- **一个 commit = 一个可独立验证的增量**；宁可步长小、次数多，不要大步子。
- 大文件（如 Reader.vue 约 1670 行）的相关改动必须拆成更小的子步骤，每子步都手测对应页面。
- 涉及数据库 schema 的步骤：先写迁移 SQL → 在**测试库**执行验证 → 再谈代码改动。

---

## 3. 变更登记与 Backlog 纪律

- 每步在 `docs/改造进度.md`（或 README 的进度段）登记一条：`[编号] 目标 | 文件 | 测试证据 | 状态`。
- 过程中发现的**与当前步骤无关**的问题：一律记入 `docs/BACKLOG.md`，不顺手改（防止范围蔓延把基线改坏）。
- Backlog 里被用户确认为重要的问题，在对应里程碑内单独立项处理，同样走 Step Loop。

---

## 4. 测试与回归定义

### 基线命令（改前/改后各跑一次）
```bash
cd server && python -m pytest tests -q          # 后端全量
cd client && npm run build                       # 前端可构建
# 受改动端点的接口冒烟（python/curl 针对该端点）
```

### 关键路径手测清单（涉及相应页面时执行）
1. 注册/登录/登出 → 进入工作台
2. AI 续写（SSE 流式输出完整、可中断）
3. 建作品 → 编辑 → 发布 → 社区可见 → 点赞/评论/收藏
4. 阅读器：进书 → 进度恢复 → 设置生效 → 书签/批注/好句落点跳转
5. 打卡 → 阅读报告/热力图数据一致
6. 通知、个人主页（等级/成就）不回归

### 测试数据隔离（一旦 M0 完成即生效）
- pytest 一律连独立测试库 `inkstone_test`，**禁止在开发库 inkstone 上跑会写数据的测试**。
- conftest 改造目标：测试库自动建表 + 每用例后清理，可重复执行、不撞唯一键/限速。

---

## 5. 红线（禁止事项，违反应当立即停下说明）

1. 禁止在本阶段新增功能模块或大范围重构"炫技"。
2. 禁止顺手改无关代码；发现的问题进 Backlog。
3. 禁止在开发库上跑会写数据的测试；禁止直接手改生产/开发数据库。
4. 禁止 rewrite 已推送的 git 历史，除非用户对具体操作明确同意。
5. 禁止绕过测试直接"感觉没问题"——完成 = 测试证据，不是自我感觉。
6. 禁止一次改动横跨两个里程碑的范围。
7. 禁止为了赶进度压缩验证步骤；宁可多停靠，不把风险往后推。

---

## 6. 里程碑停靠与汇报格式

每个里程碑（M0/M1/M2/M3）结束时**停靠一次**，向用户汇报：
- 改了什么（对照里程碑验收标准逐条给状态）
- 测试证据（pytest 结果摘要、build 结果、手测路径结论）
- Backlog 新增条目
- 下一步计划 + 需要用户拍板的事项

用户确认后再进入下一里程碑。任何时刻用户可叫停，当前已提交的增量保持可回退。
